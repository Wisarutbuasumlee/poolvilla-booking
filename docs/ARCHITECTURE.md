# Architecture

เอกสารนี้อธิบายว่าคำขอหนึ่งครั้งเดินทางอย่างไร และทำไมถึงวางแบบนี้ ข้อตัดสินใจพร้อมเหตุผลเต็มอยู่ที่ `DECISIONS.md`

## ภาพรวม

```
เบราว์เซอร์
  │
  ├─ localhost:3200            → หน้าบ้าน
  └─ admin.localhost:3200      → หลังบ้านและพอร์ทัลนายหน้า
        │
        ▼
   src/proxy.ts                bypass → intl → auth → rewrite
        │
        ├─ (public)/[locale]/…       root layout #1
        └─ (admin)/[locale]/admin/…  root layout #2
                │
                ▼
        Server Components + Server Actions
                │
        ┌───────┼────────────────┐
        ▼       ▼                ▼
    MongoDB   Redis        storage/uploads
   (replica) (rate limit,   (sharp → webp)
              hold lock)
```

## Routing

หลังบ้านอยู่ที่ path ภายใน `/{locale}/admin/...` เสมอ ไม่ว่าจะเข้ามาทางไหน hostname เป็นแค่ทางเข้า กฎข้อเดียวนี้ทำให้ route group สองอันไม่มีทางชนกันได้เลย

| เข้ามาแบบ | path ภายในหลัง proxy |
|---|---|
| `admin.localhost:3200/bookings` | `/th/admin/bookings` (rewrite แถบที่อยู่ไม่เปลี่ยน) |
| `admin.localhost:3200/en/bookings` | `/en/admin/bookings` |
| `admin.localhost:3200/th/admin/x` | redirect ไป `/th/x` แล้วเข้ารอบใหม่ |
| `localhost:3200/th/admin` | ผ่านได้เฉพาะเมื่อ `ENABLE_ADMIN_PATH_FALLBACK=true` ไม่งั้น 404 |
| `localhost:3200/th/villas` | ผ่านตรง |

### ลำดับใน proxy และเหตุผล

หนึ่งรอบของ proxy ปล่อยได้แค่ redirect หรือ rewrite อย่างใดอย่างหนึ่ง จะทำทั้งคู่ไม่ได้ ลำดับจึงถูกบังคับด้วยข้อจำกัดนี้

0. **bypass** ตัด `/api` `/_next` และไฟล์ที่มีนามสกุลออกก่อน ไม่ให้ intl หรือ auth แตะ
1. **จัดการ path หลังบ้าน** ก่อน intl เพราะถ้าปล่อยให้ intl redirect ไปก่อนจะเสียรอบเปล่า
2. **intl ตัดสินภาษา** ทำงานบนคำขอเดิม ถ้ามันตัดสินใจ redirect ให้จบรอบตรงนั้น การพยายาม rewrite ทับ response ที่มี `Location` แล้ว จะทำให้ rewrite หายเงียบ ๆ
3. **auth** ต้องรู้ locale ก่อนเพื่อสร้าง URL หน้า login และมันอาจ redirect ซึ่งอยู่ร่วมกับ rewrite ไม่ได้ (เพิ่มใน Phase 2)
4. **rewrite** เป็นขั้นสุดท้าย พร้อม forward request header ของ intl ไปด้วย ไม่งั้น subtree ที่ถูก rewrite จะไม่รู้ locale แล้ว `useTranslations` จะ throw

ถ้าสลับให้ rewrite มาก่อน intl จะเห็น path ที่มี `/admin` ติดอยู่ แล้ว `hreflang` กับตัวสลับภาษาจะพ่นลิงก์ผิด

### cookie ของนายหน้า

`?ref=<agentCode>` ถูกเก็บลง cookie `pv_ref` อายุ 30 วัน และต้องเซ็ตใน **ทุกทางออก** ของ proxy รวมถึงขาที่ redirect เปลี่ยนภาษา เพราะลิงก์ที่นายหน้าส่งจริงคือ `/villa/DV-2685?ref=123` ซึ่งไม่มี locale นำหน้า สิ่งแรกที่เกิดกับมันคือ redirect ถ้าเซ็ต cookie เฉพาะขาที่ผ่านตรง จะเสีย referral บนลิงก์ที่นายหน้าใช้จริงทุกเส้น

proxy ตรวจแค่รูปแบบของรหัส ส่วนการตรวจว่านายหน้ามีจริงและยัง active อยู่ไหม เป็นหน้าที่ของชั้น resolve ราคาซึ่งเข้าถึงฐานข้อมูลได้

### สอง root layout

ไม่มี `src/app/layout.tsx` โดยตั้งใจ การมี root layout สองอันต้องไม่มีตัวครอบที่ราก ไม่งั้นจะได้ `<html>` ซ้อนกัน สองพื้นผิวนี้อยู่คนละ hostname มีคนละ chrome คนละ metadata และไม่มีการนำทางฝั่ง client ข้ามกัน จึงไม่ได้อะไรจากการใช้รากร่วมกัน

`[locale]` ปรากฏสองที่ ทั้งคู่ re-export `generateStaticParams` จาก `src/i18n/static-params.ts` เพื่อไม่ให้สองสำเนาหลุดจากกัน

ทุก page และ layout เรียก `setRequestLocale(locale)` เป็นบรรทัดแรกที่แตะ locale ไม่งั้น next-intl บังคับทั้ง subtree ให้เป็น dynamic

## ราคา

### สองชั้น

```
ราคาคืนหนึ่ง = resolveBase(คืนนั้น) + markup[ประเภทวันของคืนนั้น]

resolveBase  ตัดสินตามลำดับ  ช่วงเทศกาลของบริษัท
                              → วันหยุดนักขัตฤกษ์
                              → เสาร์ → ศุกร์ → อาทิตย์ถึงพฤหัส
```

ประเภทวันตัดสินจาก **คืนที่เข้าพัก** ไม่ใช่วันเช็คเอาท์ เข้าศุกร์ออกเสาร์คือหนึ่งคืน ประเภท `FRI`

เมื่อคืนหนึ่งโดนราคาช่วงเทศกาลทับ ยอดบวกเพิ่มยังถูกบวกตามประเภทวันเดิมของคืนนั้น

### เอนจินเป็นฟังก์ชันบริสุทธิ์

`src/lib/pricing/` ห้าม import `@/lib/db` หรือ mongoose ทุกอย่างรับเข้ามาเป็นอาร์กิวเมนต์ ESLint บังคับไว้

ผลที่ได้คือหน้าค้นหา 20 หลังคำนวณราคาโดยไม่ยิง query เพิ่มเลย หน้าเพจดึงข้อมูลเป็นชุดครั้งเดียว แล้วเรียก `quote()` ยี่สิบครั้งในหน่วยความจำ ซึ่งใช้เวลาระดับไมโครวินาที

`quote()` ไม่ throw เมื่อผิดกฎธุรกิจ มันคืน `violations` พร้อมยอดที่คำนวณไว้ เพื่อให้หน้าเว็บบอกได้ว่า "ช่วงนี้ขั้นต่ำ 3 คืน ถ้าจองครบจะเป็นเท่านี้" แทนที่จะขึ้นข้อความ error เปล่า ๆ

### เมื่อช่วงเทศกาลทับกันหลายอัน

ตัดสินด้วยลำดับตายตัว ระบุประเภทวันเจาะจงชนะ `ALL` → ช่วงสั้นชนะช่วงยาว → เริ่มทีหลังชนะเริ่มก่อน → ราคาสูงชนะราคาต่ำ → เรียงตาม id

ข้อสุดท้ายทำให้ผลลัพธ์ไม่ขึ้นกับลำดับใน array ซึ่งลำดับของ subdocument ใน Mongoose ไม่ใช่การตัดสินใจทางธุรกิจ

### วันหยุดต่อเนื่องเก็บเป็นแถวจริง

เอนจินไม่เดาว่า "พรุ่งนี้เป็นวันหยุดไหม" ตาราง `holidays` เก็บแถว `type: 'long_weekend'` สำหรับวันก่อนวันหยุดยาวโดยตรง แอดมินแก้ได้และตรวจย้อนหลังได้ ซึ่งสำคัญเวลานายหน้าเถียงเรื่องบิล

## ปฏิทินว่างและการกันจองชน

**การไม่มีเอกสารแปลว่าว่าง** เก็บเฉพาะวันที่ไม่ว่าง ปฏิทิน 10 หลังสองปีจึงเป็นเอกสารไม่กี่พันแถว ไม่ใช่ 7,300 แถวที่เขียนว่า available

**คืนคือช่วง `[checkIn, checkOut)`** วันเช็คเอาท์ไม่เคยถูกกัน ทำให้เช็คเอาท์เที่ยงเช็คอินบ่ายวันเดียวกันทำงานได้โดยไม่ต้องมีเคสพิเศษ ทุก UI ปฏิทินต้องวาดตามนี้ ไม่งั้นจะดูเหมือนคลาดไปหนึ่งวัน

**กลไกความถูกต้องคือ unique index บน `{villaId, dateKey}`** ไม่ใช่ transaction การจองค้างยิง `bulkWrite` แบบ `ordered: false` เป็น conditional upsert ทุกคืนพร้อมกัน คืนที่ว่างจะ insert สำเร็จ คืนที่คนอื่นถืออยู่จะชน `E11000` ทำให้รู้ทุกคืนที่ชนในรอบเดียว ถ้าได้ไม่ครบก็ลบเฉพาะของตัวเองด้วย `deleteMany({villaId, bookingId})`

`bookingId` ถูกสร้างก่อนแล้วใช้เป็นทั้ง token ของ hold และ `_id` ของ booking ทำให้เอกสารปฏิทินทุกใบบอกได้ตั้งแต่วินาทีแรกว่าเป็นของการจองไหน

**การอ่านถือว่า hold ที่หมดอายุแล้วเท่ากับว่าง** ต่อให้ตัวกวาดล้างตาย ลูกค้าจริงก็ไม่โดนบล็อก นี่คือชั้นความทนทานที่สำคัญที่สุดของกลไกนี้

## แคชกับ cookie ของนายหน้า

หน้ารายละเอียดบ้านต้องแยกเป็นสองส่วน

- **เนื้อหาบ้าน** แกลเลอรี สิ่งอำนวยความสะดวก ห้องนอน SEO ไม่ขึ้นกับนายหน้า แคชได้ แล้ว revalidate ด้วย tag ตอนแอดมินบันทึก
- **กล่องราคา ตารางราคา ปฏิทิน** ขึ้นกับ cookie จึงอยู่ใน `<Suspense>` boundary แยกที่เป็น dynamic

ถ้าไม่แยกจะเจอสองอย่าง คือทั้งหน้ากลายเป็น dynamic ทำให้ Lighthouse ตก หรือแย่กว่านั้นคือหน้าที่แคชไว้เอาราคาของนายหน้าคนหนึ่งไปแสดงให้ลูกค้าของอีกคน

## ความไม่เปลี่ยนแปลงของเอกสารการจอง

ราคาที่นายหน้าตั้งเปลี่ยนได้ตลอด การจองที่เกิดไปแล้วต้องไม่เปลี่ยน ตอนสร้างต้องบันทึก

- `agentId` `agentCodeSnapshot` `villaCodeSnapshot`
- `priceBreakdown` ทั้งชุด รวมเหตุผลของราคาแต่ละคืน
- `rateCardSnapshot` ทั้งราคาฐานและยอดบวกเพิ่มที่ใช้จริง
- `commission` อัตราตอนนั้น
- `pricingEngineVersion`

รายงานทุกตัวอ่านจาก `priceBreakdown.grandTotal` ห้าม join กลับไปที่ `villa_agents`

ประกันความเสียหายไม่เข้ายอดรวม ไม่เข้าค่าคอม ไม่เข้า ADR โดย ADR คิดจาก `accommodationTotal / nights` ไม่ใช่ `grandTotal / nights`

## Storage

รูปเข้ามาผ่าน Server Action แล้ว sharp แปลงเป็น WebP หลายขนาด เก็บลง `./storage/uploads` และเสิร์ฟผ่าน route handler ไม่ใช่ `public/`

ทุกอย่างผ่าน `StorageAdapter` เพื่อให้ย้ายไป S3 หรือ MinIO ได้โดยไม่ต้องแก้จุดเรียกใช้

## การแจ้งเตือน

อีเมล LINE และ Telegram เป็น adapter ที่ปิดเปิดด้วย env ตัวที่ไม่ได้ตั้งค่าจะถูกข้ามเงียบ ๆ ไม่ทำให้การจองล้ม
